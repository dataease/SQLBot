# TAPD 规格、任务与附件

当前创建批次已确认选择 TAPD，或读取、更新已有 TAPD 单据时采用本流程。
新批次的平台确认见 [issue-tracker.md](issue-tracker.md)，角色标签见 [triage-labels.md](triage-labels.md)。

## 核对项目空间

- 先根据当前仓库及远端确认项目身份，再查对应的 TAPD 项目空间；不能未经核对就沿用其他仓库、上一次任务或个人配置中的项目 ID。
- 本仓库映射于 2026-11-09 核实：GitHub `dataease/SQLBot` 对应 TAPD 项目 `SQLBot`，`workspace_id` 为 `33458688`。该映射是定位线索，写入前仍需核对当前项目名称、ID 和目标单据归属。
- 可通过项目配置、来源单据及当前账号参与的项目列表核实。项目列表要区分项目与公司/组织；存在同名项目、映射缺失或归属不一致时，先请用户确认具体空间，不能猜测。
- 这里的 `workspace_id` 是 TAPD 项目空间 ID，不是 SQLBot 产品内工作空间的 `oid` 或 `workspace_id`。
- 创建需求、任务、评论和上传附件时显式传入已核实的 TAPD `workspace_id`；完整实体 ID、关联类型和所属项目必须一致。

## 发布前确定范围与承载形式

1. 完成项目空间核对，再核实来源实体类型和完整 ID，读取最新描述、评论及关联规格。长 ID 按字符串处理，避免 JavaScript 数字精度丢失。
2. 区分问题记录、方案验证、已确认规格和实施任务。方案尚未选定时，如实标注待决策项；不要把研究结论发布成已选定的实施方案。
3. 已指定需求、评论或附件位置时沿用；只有承载形式仍不明确且影响关联方式时才澄清。发布、上传、修改状态和开始实现是不同动作，按已获授权的范围执行。

需要原生需求—任务关系时，用需求/工作项承载 spec，再将 task 关联到该需求。
任务的 `story_id` 指向需求，不能填缺陷 ID 或评论 ID；参见 [官方任务字段](https://open.tapd.cn/document/api-doc/API%E6%96%87%E6%A1%A3/api_reference/task/add_task.html)。
有来源缺陷时，通过平台支持的缺陷—需求关联保留来源，按授权范围操作。
已选择“缺陷评论保存 spec”时保持该形式，不自动另建需求或转换来源缺陷。

## 保存和更新 spec

- 使用技能要求的规格模板，综合已有讨论；沿用已确认的验收接缝，不重新访谈已决定的问题。明确方案、验收、未决项、实验限制及实施授权状态。
- 评论保存的是完整规格正文，不是一个文件附件。Markdown 可能由连接器转换为富文本；发布后检查章节、列表、链接和关键内容。
- 更新已有 spec 时定位同一规格载体（需求正文、缺陷正文或评论），写入前重新读取并检查是否有并发编辑。保留外部新增内容，不用本地旧快照盲目覆盖；不要每次更新都新增一条完整规格评论。
- 记录来源单据链接及承载规格的实体/评论 ID。后续实现依据已确认规格和最新明确指令，实验报告中的历史待定结论不覆盖当前决定。
- “讨论阶段未授权实施”是阶段记录。用户后来明确要求 implement 对应任务时，该指令就是实施授权，不因旧句子再重复确认。

## Markdown 附件与交接入口

- 在用户授权的文档范围内上传相关规格和报告；只上传已审阅文件，排除凭据、日志、本机绝对路径和无关工作区内容。
- 规格正文必须列出配套附件的文件名、用途和读取顺序，并区分当前规格与历史实验证据；仅在明确保留 Git 副本时列出仓库路径。
- 文件在需求或缺陷附件区保存时，任务正文应指向该来源单据并写明附件名。不要只提供本机会失效的临时目录。
- 资料归属按 [issue-tracker.md](issue-tracker.md) 执行。交接使用规格所在单据及附件索引，本地临时目录不作为唯一来源；实验包应可在仓库外解压运行。
- 以确认后的规格为主版本，同步正文与 Markdown 附件；只有存在明确的 Git 副本约定时才同步仓库快照。用户已下载的副本不会自动更新。
- 替换附件前核实覆盖能力和同名文件；替换可能返回新的附件 ID。按来源实体、文件名及当前附件记录核对，不假设旧 ID 永久对应最新版。
- 下载链接可能有短期有效期。交接记录使用实体链接、附件名和必要的附件 ID，读取时重新获取下载链接。

## 拆分和发布 tickets

1. 从完整 spec 及来源讨论提取纵向切片，每票交付可演示或验证的完整行为，包含所需实现和测试。共用基础能力可以随首个闭环建立，不默认拆成建表、评分、测试等纯横向票。
2. 展示标题、直接阻塞项和交付行为，按 `to-tickets` 要求取得拆分认可后再发布。后续只对真正改变范围或依赖的问题澄清。
3. 先创建无阻塞票，再按依赖顺序创建后续票，用已返回的真实 ID 和链接填写 `Blocked by`。仅列直接依赖，传递依赖可沿前置票追溯。
4. 每票的 `Parent` 指向实际规格位置：正文规格链接到承载单据，评论规格同时写明评论 ID；有配套附件时列出文件名。写明验收条件和实施边界，使用项目实际支持的标签字段设置 `ready-for-agent`，保留任务未开始状态。设置负责人、日期、迭代或改变来源状态须有相应任务依据。
5. 优先使用当前实体类型支持且可验证的原生关联和阻塞关系。缺少可用写入口时，在正文保存关系并明确说明，不宣称已建立原生父子关系或平台强制阻塞。
6. 取得真实任务 ID 后，回读同一 spec，在正文顶部维护“实施任务与依赖”索引，逐票列出标题、可点击链接和直接前置任务；无前置时写“无”。需求正文、缺陷正文和评论规格均须建立此反向入口，已有原生关联也保留索引。同步修正“尚未创建任务”等过时表述；任务状态以远端实时记录为准。
7. 交付前逐票回读，确认 spec 索引覆盖本次全部任务、每票 `Parent` 指回同一规格，且索引、`Blocked by` 与已建立的原生依赖一致。新增、拆分、合并或调整依赖时同步相关票和索引；有遗漏则补齐后再报告发布完成。部分发布失败时保留已创建任务及其索引，明确剩余项，重试前查重。

发布已确认 spec 的 tickets 时，维护上述双向索引属于本批发布范围，无需另行询问。
父单据的修改限于任务索引及相关过时表述，保留需求内容、外部新增内容、负责人和状态，不关闭父单据。
用户明确要求只创建任务或保持 spec 不变时，遵循该限制，并在交付中注明反向索引未同步。

缺陷或评论规格采用正文双向引用，原生任务归属按“发布前确定范围与承载形式”处理。
后续执行从前置任务均已完成的票开始；发布及索引同步不等于开始实施。

## 连接器能力与回读核对

- 区分当前可调用工具、已安装客户端及 TAPD 平台能力。工具列表没有上传入口，不等于平台不支持附件。先核对现有接口；确实缺能力时，在用户已授权范围内使用同一项目的官方客户端或网页，并说明方式。
- 使用既有安全配置加载，保持个人令牌和项目一致，不回显凭据、不借用其他项目配置、不为完成发布擅自扩大工具白名单。不要把某次连接器的创建/更新封装细节写成永久通用规则。
- 写入超时或结果不明确时，先按目标实体、标题或附件名查询，确认是否已落库，再决定是否重试，避免重复单据和附件。
- 写后回读，核对实体类型、项目和完整 ID，以及正文、状态、标签；spec 与 tickets 按上述双向索引完成条件核对。附件核对文件名、关联实体和最新版记录。需要证明内容一致时下载后比较摘要；只查到附件列表不能称为文件内容校验通过。
- 交付列出可点击的规格/任务入口、依赖关系及实际关联方式，说明是否只发布文档、是否已实施、是否已提交或部署。不要把这些状态混为一谈。
